# claude-jam — Prior Art Survey

Research date: **2026-08-28**. Scope: anything that puts **2+ humans into one live AI coding-agent session**, for Claude Code and for peer agents (Codex CLI, Gemini CLI, Cursor, Aider, OpenCode, Amp, Cline, Copilot CLI, Devin), plus adjacent multiplayer/pair-programming-with-AI products and the raw terminal-sharing layer underneath them.

claude-jam's five-part design bar, used as the scoring rubric throughout:

1. **Multi-human** — 2+ different people, on different machines, typing into one live session.
2. **Attribution to agent** — the model itself is told who wrote each message.
3. **Human-only channel** — a side channel the agent never sees.
4. **Presence / typing** — everyone sees everything, plus live typing indicators.
5. **Preserves native env** — the host keeps the real `claude` TUI in tmux, with their own plugins, skills, and MCP servers.

---

## 1. TL;DR

- **Nobody does exactly this.** Across ~40 verified projects and features, not one hits all five criteria. The combination that is genuinely unclaimed is *attribution-to-agent* plus *human-only side channel* plus *native TUI preserved*. Every project that has two of those three is missing the third.
- **Closest three:** (1) **[manycode / ccshare](https://github.com/unworld11/ccshare)** — real PTY around the real agent binary, up to 5 joiners, and a genuine human-only chat channel; fails only on attribution ("all input appears unified to the agent"). (2) **[claude-threads](https://github.com/anneschuth/claude-threads)** — spawns a real local `claude` process per Slack/Mattermost thread with `!invite` multiplayer and `Co-Authored-By` attribution; fails on side channel, presence, and it re-renders the TUI as chat. (3) **[claude-code-collab](https://github.com/jxandery/claude-code-collab)** — a 14-commit hobby repo that is architecturally the same idea as claude-jam (shared tmux pane, wrapper prefixes `[Username]` before `send-keys`), which is the strongest evidence that the idea is obvious *and* that nobody has actually built it properly.
- **What nobody does:** feed per-message human identity into a *shared PTY* session. Every terminal-sharing tool (tmate, upterm, sshx, Zellij, ttyd, Warp, Termius, Live Share) merges keystrokes into one anonymous stdin. Every tool that *does* have attribution (claude-threads, llmcord, Poe, Devin-in-Slack, Mastra) got it for free from a chat platform's sender field and gave up the native TUI to get it. claude-jam is the only design found that tries to have both.
- **What we should borrow:** manycode's **6-character join code + bundled Cloudflare Quick Tunnel** (outbound-only, no port forwarding, no relay account) and its **secret-masking of `.env` values** in the mirrored stream; claude-duet's **approval mode** (host reviews a partner's prompt before it executes) and its **`@claude`-prefix convention** that cleanly separates side-chat from prompts; claude-threads' **`Co-Authored-By` commit trailers per participant** and **emoji-reaction permission approvals**; multAIplayer's framing of teammate input as **explicitly untrusted context** in the prompt; Zellij's **per-client independent pane focus** as the eventual multi-cursor model.
- **Where we're behind:** access control (manycode, claude-jam, and most peers treat the join code as the only auth — upterm's per-user pubkey auth is the correct answer), transport encryption (claude-duet uses WebRTC + NaCl, multAIplayer uses RFC 9420 MLS, CoAgent uses X25519+AES-GCM), and durability/reconnect (Warp, Zellij, and Superlogical all treat session resurrection as a first-class feature).

## 3. Deep dives

### manycode (formerly ccshare) — the closest thing that exists
`manycode` wraps whatever agent binary you hand it in a `node-pty` PTY and mirrors the terminal frames over WebSocket to up to five joiners, who attach either from their own terminal or from an xterm.js browser client using a **6-character session code**. Connectivity is deliberately layered: on a LAN it discovers the host by UDP broadcast and connects directly over `ws://`; remotely it starts a **bundled Cloudflare Quick Tunnel** so the host only ever makes an outbound connection (no port forwarding, no relay account, no inbound firewall rule), with Tailscale direct-IP and a self-hosted "dumb pipe" relay as alternatives — the relay never sees plaintext. The PTY resizes down to the smallest attached terminal. It proves the whole native-environment thesis: the real CLI runs, plugins/skills/MCP are untouched, and a shared PTY over a tunnel is enough for real collaboration. **What it lacks is exactly our differentiator**: the README states plainly that all input appears unified to the agent, so Claude cannot tell who typed what — it is a shared keyboard, not a shared conversation. It does have a real human-only channel (`Ctrl-T` in the CLI, sidebar in the browser, `manycode say` from a script) that "never touches the shared prompt," and it stamps names on *those* messages only. Presence is coarse: the window title shows `CODE · N connected` and the host's terminal rings a bell on join/leave; there is no typing indicator. Security is thin by admission — "the code is the only auth" — mitigated by an `--approve` flag that makes the host confirm risky commands, automatic masking of `.env` secret values in the mirrored stream, and optional asciinema recording. **Steal:** the 6-char code + bundled Quick Tunnel connectivity ladder, the secret-masking filter, and `--approve`.

### claude-threads — attribution done right, at the cost of the TUI
An Apache-2.0 TypeScript bot (39★, 947 commits, pushed the day of this survey) that spawns a **real local `claude` CLI process** per Slack or Mattermost thread, isolated in its own git worktree, and bridges the PTY into the thread through an MCP server. The tagline — "screen-sharing for AI pair programming, but everyone can type" — is the same pitch as claude-jam. The session owner runs `!invite` to add collaborators; each invitee registers a `!github-email` and their contributions land as `Co-Authored-By` trailers on the resulting commits, which is the cleanest attribution artifact found anywhere in this survey. Permission prompts, plan approvals, and questions are answered by **emoji reactions on the bot's own message** — an elegant trick that avoids a second UI entirely. Non-invited users' messages are gated behind a 👍 from the owner. The README is explicit that sessions "use your local checkout plus whatever MCP servers and plugins you already configured," so it preserves the real environment — but it re-renders everything as chat messages, task-list stickies, and reaction prompts, so the *native TUI itself* is gone, and there is no typing indicator and no side channel (approvals happen in the very thread the agent reads). **Steal:** `Co-Authored-By` per participant, emoji-reaction approvals, and owner-gated admission for uninvited speakers.

### claude-code-collab — our architecture, built in a weekend and abandoned
Zero stars, 14 commits, untouched since 2026-03-07, MIT. A shared tmux session over SSH; each collaborator runs a local wrapper script that prompts them for input and then `tmux send-keys` it into the one server-side pane running `claude`, **auto-prefixed with `[Username]`**. That is a bare-bones version of exactly what claude-jam does, and it validates the mechanism: string-prefixing before injection is sufficient to give the model per-speaker attribution inside a real TUI, with no protocol changes and no SDK. The README tells users to go use Zoom, Discord, or Slack for human-to-human chatter — i.e. it identified the side-channel need and punted. No presence, no typing indicators, no access control, no reconnect. **Its existence is the single best evidence in this report** that the idea is obvious to reach for and that no one has followed through: the closest architectural match to our design has literally never been used by anyone.

### multAIplayer — the same idea, properly engineered, for Codex
Apache-2.0, 728 commits, macOS Apple Silicon alpha, last commit ~2026-07-21. The host runs the real local **Codex app-server**; a single-node SQLite-backed relay routes **RFC 9420 MLS** end-to-end-encrypted records over WebSocket between teammates' browsers and CLIs. There is a shared PTY, an approval workflow where the host approves room turns, and — notably — **the ability to hand hosting between teammates**, which no Claude-side project offers. Its most transferable idea is a prompt-safety one: teammate messages, file contents, terminal output, and browser input are all **explicitly labeled as untrusted context** when formatted into the model's input, which is the correct way to think about a session where several people (and a relay) can inject text. Because that team chat is fed to Codex as context, it is not a human-only channel; there are no typing/presence indicators. **Steal:** the untrusted-context labeling convention, host handoff, and MLS as the eventual answer if we ever need real E2E group encryption.

### claude-duet — the only project with both a side channel and typing indicators
MIT, 143★, 73 commits, last commit 2026-03-19. Strictly two humans: a host and a partner. The default transport is a **WebRTC P2P data channel** encrypted end-to-end with NaCl secretbox and scrypt-derived keys, so there is no relay in the happy path at all; localtunnel, SSH, and Cloudflare tunnels are fallbacks. Its interaction model is the sharpest of any project here: **plain messages are partner-only chat that never reaches Claude, and only `@claude`-prefixed messages become prompts** whose responses both humans see. It shows an inline typing indicator, and an "approval mode" (on by default) lets the host review the partner's prompt before it executes. The catch is the whole point of claude-jam: it drives Claude **headless via the Agent SDK**, not the interactive TUI, so plugin/skill/MCP fidelity is unverified and the host loses their own terminal. It also does not attribute individual messages to their author for the model. **Steal:** the `@`-prefix convention as an alternative to a separate channel widget, and approval-mode as a default-on safety gate.

### CoAgent — a different topology worth understanding
No public repo (a ~3.9 MB Node package for $5, or a free "build it yourself" prompt), so traction and license are unverifiable, but the architecture is instructive: instead of sharing one agent, it **bridges two or more separate native Claude Code sessions**, one per human, each with MCP tools registered to read/send messages and share files through an E2E-encrypted relay (X25519 key exchange, AES-256-GCM) that never reads content. Pairing is an 8-character code. It maintains a dedicated **Human Chat** channel plus a separate "AI Interactive Chat" for shared instructions to both agents. This is the "federated" alternative to our design: everybody keeps their own agent, context diverges, and the relay is only a message bus. Worth naming in our own docs as the road not taken — it avoids all turn-taking problems and gains nothing shared.

### Warp Agent Session Sharing — the commercial ceiling today
Warp extended its ordinary terminal session sharing to cover agent activity: prompts, responses, thinking, tool calls, and terminal output sync through **Warp's cloud** to viewers who join from the Warp app, any browser, or mobile. Collaborators granted edit access can type into the prompt, send new agent queries, and execute commands — genuine multi-human control of one live agent session, with named avatars and cursors for presence. Since Warp's April 2026 "Universal Agent Support," the agent inside can be Claude Code, Codex, Gemini CLI, OpenCode, Amp, or Cursor running as real CLI processes in Warp panes, and Warp's own client went dual MIT/AGPLv3 on 2026-04-28. Two structural gaps versus claude-jam: it only works **because you live inside Warp's terminal**, not your own tmux with your own config, and there is no evidence per-person identity ever reaches the agent. Sessions also expire in about a week — it is a share, not a durable pairing surface. This is the bar to beat on polish, and the reason our pitch is "your terminal, not ours."

### The raw terminal-sharing layer (tmate → upterm → sshx → Zellij → ttyd)
All of these run any program, including a `claude` TUI, and merge every attached client's keystrokes into a single anonymous stdin. They differ only in transport and identity-of-humans-to-humans: **[upterm](https://github.com/owenthereal/upterm)** (1.3k★, Apache-2.0) is the security high-water mark — per-user GitHub/GitLab/SourceHut/Codeberg pubkey authentication, a read-only mode, and host approval for SFTP/SCP file operations, all of which tmate and sshx lack; **[sshx](https://github.com/ekzhang/sshx)** (7.7k★, MIT, quiet since 2025-06-19) has the best presence UX, a Google-Docs-like infinite canvas with named colored remote cursors, but explicitly does not support self-hosting; **[Zellij](https://zellij.dev/tutorials/web-client/)** (35.2k★, MIT, pushed the day of this survey) is the strongest foundation — genuine multiplayer since v0.23.0 with per-client cursors, and as of v0.45.0 (2026-08-20) clients can independently focus different panes and tabs, plus a token-authenticated HTTPS web client and session resurrection; **[ttyd](https://github.com/tsl0922/ttyd)** (12.3k★) is the minimal case, any number of browser tabs on one PTY with no UI at all. **The shared conclusion:** none of them has any concept of telling the program inside the pane who typed. That is a layer nobody has built, and it is precisely claude-jam's layer. **Steal:** upterm's pubkey-per-collaborator auth model (our join code is weaker than it should be), and Zellij's independent-per-client focus as the model if we ever want multiple humans in different views of the same session.

### Zed's Agent panel — the mainstream idea, one layer up
Zed (89.4k★, GPL-3.0-or-later + Apache-2.0, daily commits) reuses the **CRDT collaboration layer it already had for human-to-human editing** to stream an agent's edits and cursor live to everyone in a channel; humans watch the agent work and approve or reject a unified diff before it lands. Channels carry persistent notes and voice chat, which is a real human-only side channel sitting right next to the agent's work. This is the closest mainstream expression of "several humans and an agent share one live surface with presence" — but it operates at the **editor-buffer/document** level rather than a terminal session, and the agent is Zed's own (BYO model over API/ACP), not an external CLI running in its native environment. No evidence the agent is told which human authored which instruction. **Steal:** conceptually, that presence + diff-approval + a voice/notes side channel is a complete and shippable interaction model; the CRDT approach also shows that a document, not a keystroke stream, is the right abstraction if we ever outgrow the PTY.

## 4. Patterns to borrow

**Speaker tagging.** Chat-completion APIs mostly lack a real multi-speaker primitive — OpenAI's `name` field on Chat Completions was the closest thing and it was **dropped with no replacement in the Responses API** ([community thread](https://community.openai.com/t/dealing-with-multiple-participants-using-the-responses-api-message-name/1154818)); Anthropic's [Messages API](https://docs.anthropic.com/claude/reference/messages-examples) has only generic `user`/`assistant` roles. So every working implementation does it by **prompt templating**: [llmcord](https://github.com/jakobdylanc/llmcord) prepends `Username: message` while walking the Discord reply chain; [claude-code-collab](https://github.com/jxandery/claude-code-collab) prefixes `[Username]` before `tmux send-keys`; [Mastra](https://mastra.ai/blog/building-multi-user-multi-channel-agents) passes per-message user identity as signal metadata so "the model knows who sent each message." Template-prefixing is the industry-standard answer, not a hack — and the corollary from [multAIplayer](https://github.com/maddiedreese/multAIplayer) is to label everything a teammate injects as **untrusted context** in the same breath.

**Turn-taking and concurrency.** Three distinct models are in production. *Queue* — [Bolt.new](https://support.bolt.new/building/using-bolt/collaborate) runs a single shared chat thread with a **sequential prompt queue** so simultaneous prompts serialize; Mastra names the same options explicitly as **queue / debounce / batch** modes. *Control handoff* — [Termius](https://termius.com/blog/from-chaos-to-clarity-reimagining-real-time-collaboration-in-the-terminal) gives one driver at a time with a cursor showing who has it, and [multAIplayer](https://github.com/maddiedreese/multAIplayer) lets the host role itself move between teammates. *Host approval* — [claude-duet](https://github.com/EliranG/claude-duet)'s default-on approval mode makes the host confirm a partner's prompt; [claude-threads](https://github.com/anneschuth/claude-threads) gates uninvited speakers behind a 👍; [manycode](https://github.com/unworld11/ccshare)'s `--approve` gates risky commands. Approval is the pattern with the most independent adoption — three separate projects converged on it.

**Separating human chatter from agent instructions.** Four approaches, in descending elegance: a **prefix convention** (`@claude` in claude-duet — no extra UI, zero risk of leaking to the model, works in a plain text stream); a **separate channel that structurally cannot reach the agent** (manycode's `Ctrl-T` chat, CoAgent's Human Chat, Zed's channel notes/voice); **out-of-band tooling by instruction** (claude-code-collab's README: go use Zoom); and **making the control path un-callable by the agent** — the [WhatsApp channel plugin](https://github.com/rich627/whatsapp-claude-plugin) keeps access approval as a terminal command and states it is "deliberately not an MCP tool, so nothing arriving over WhatsApp can reach it." That last one is the right security posture for any privileged action in a multi-writer session and generalizes directly to our design.

**Presence.** Cheapest useful signal is a **connected count plus a bell** (manycode's window title and join chime). Next tier is **named colored cursors** — [sshx](https://github.com/ekzhang/sshx), [Zellij](https://zellij.dev/tutorials/web-client/), [Warp](https://docs.warp.dev/agent-platform/local-agents/session-sharing/), [Agor](https://github.com/preset-io/agor)'s facepile, and GitHub Next's Ace all landed here independently. Actual **typing indicators** are rare and only appear where there is a chat surface to hang them on: claude-duet (inline), [Conductor](https://www.conductor.build/) (presence dots *and* typing), Bolt.new ("you'll see when others are typing"). Zellij's v0.45.0 step — letting clients focus different panes/tabs while sharing one session — is the frontier.

**Relay and auth models.** Ranked by how much trust the relay needs: **P2P with no relay** (claude-duet WebRTC + NaCl secretbox/scrypt; Termius WebRTC with signaling-only servers) → **E2E over a blind relay** (multAIplayer with RFC 9420 MLS; CoAgent with X25519 + AES-256-GCM; sharemyclaude with AES-128-GCM keyed from the URL fragment) → **outbound tunnel, no account** (manycode's bundled Cloudflare Quick Tunnel, plus Tailscale direct-IP) → **trusted cloud relay** (Warp, sshx on Fly.io + Redis, Live Share, Code With Me). On admission control: a **short join code as sole auth** is the norm and is weak (manycode says so outright: "the code is the only auth"); [upterm](https://github.com/owenthereal/upterm) is the only tool here with real per-collaborator identity — GitHub/GitLab pubkey auth plus a read-only mode and host approval for file operations. Zellij's web client uses **token-authenticated HTTPS** with bookmarkable per-session URLs, a reasonable middle ground.

## 6. Gaps / our differentiation

**Genuinely unique to claude-jam, as of 2026-08-28:**

1. **Per-message attribution to the agent inside a shared native session.** Every project that has attribution got it from a chat platform's sender field and gave up the TUI (claude-threads, Devin-in-Slack, llmcord, Poe, Mastra). Every project that keeps the native PTY loses attribution to keystroke merging (manycode, sharemyclaude, claude-code-web, tmate/upterm/sshx/Zellij/ttyd, Warp, Live Share). The only project that does both is [claude-code-collab](https://github.com/jxandery/claude-code-collab) — 0 stars, 14 commits, dead since March.
2. **Attribution *and* a human-only channel *and* the native TUI, together.** manycode has channel + TUI, no attribution. claude-duet has channel + typing, no TUI, no attribution. claude-threads has attribution + real process, no channel, no TUI. CoAgent has channel + native TUI but federates separate agents rather than sharing one. No project holds all three.
3. **Typing indicators over a shared PTY.** Typing indicators exist only where a chat UI exists (claude-duet, Conductor, Bolt.new). No terminal-sharing tool has them; the best any PTY tool does is a connected count and a join bell (manycode) or a cursor (sshx, Zellij).
4. **Host keeps the real environment.** Warp requires Warp. Conductor, Clay, Agor, MADE, Ace, and claude-code-web all replace the terminal with a browser UI. Claude Tag, Slack Code, Cursor-in-Slack, Codex-in-Slack, and Devin all run server-side. Our host runs their own `claude` with their own plugins, skills, and MCP servers in their own tmux, and that is a real and defensible difference.

**Where we are behind:**

- **Admission control.** A join code as sole auth is the ecosystem norm and it is the ecosystem's weakest point. [upterm](https://github.com/owenthereal/upterm) already solved this properly with per-collaborator pubkey auth from GitHub/GitLab plus a read-only mode; Zellij uses token-authenticated HTTPS. We should have at least read-only guests and per-participant identity before this is shared beyond a trusted team.
- **Transport encryption.** claude-duet (WebRTC + NaCl secretbox/scrypt), multAIplayer (RFC 9420 MLS), and CoAgent (X25519 + AES-256-GCM) all ship E2E encryption where a relay exists. Anything relayed and unencrypted is behind the field.
- **Approval gating.** Three independent projects converged on host-approves-teammate-input as a default (claude-duet's approval mode, claude-threads' 👍 gate, manycode's `--approve`). If a joiner's message can trigger a tool call in the host's real repo with the host's real credentials, this is table stakes, not a feature.
- **Secret hygiene.** manycode masks `.env` values in the mirrored stream. A PTY mirror will otherwise happily broadcast any token that scrolls past.
- **Durability and reconnect.** Warp, Zellij (session resurrection), and Superlogical all treat "the session survives disconnects and comes back" as core. Ours should not lose the room when a laptop sleeps.
- **Host handoff.** multAIplayer can move the host role between teammates. Nothing on the Claude Code side can.
- **Polish and reach.** Warp and Conductor have avatars, cursors, mobile clients, and billing. We have a tmux wrapper. That is the correct trade for now, but it is the axis on which a commercial competitor would win.
